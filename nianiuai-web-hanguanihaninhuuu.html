    7.1. 简介

    一位零售商希望管理其店铺中销售的商品。他家中已有用于此目的的 Access 应用程序，但对网络世界充满向往。他在一家互联网服务提供商处拥有一个账户，该服务允许客户在其个人文件夹中安装 PHP 脚本，从而创建动态网站。此外，这些客户还拥有一个 MySQL 账户，可用于创建表以向 PHP 脚本提供数据。 因此，这位店主拥有一个 MySQL 账户，登录名是“adarticles”，密码是“mdparticles”。他有一个名为“darticles”的数据库，并对该数据库拥有完全访问权限。因此，我们的商家已经具备了将产品管理系统上线所需的一切条件。在您的帮助下——因为您具备 Web 开发技能——他正着手开展这项工作。

    7.3. 项目约束

    该商户正在将一个本地 ACCESS 应用程序迁移至 Web 应用程序。他尚不清楚该应用程序的未来走向或发展路径。但他希望新应用程序易于使用且具备可扩展性。因此，其 IT 顾问在设计表结构时设想了以下情况：

    • 拥有不同权限的各类用户：这将使商家能够将某些任务委派给他人，而无需授予其管理员权限
    • 未来可能需要除ARTICLES表以外的其他表

    同一位顾问还提出了其他建议：

    • 他深知在软件开发中，展示层与处理层必须明确分离。Web 应用程序的架构通常如下：

    • 我们将把应用程序的业务逻辑置于一个 PHP 类中。因此，上文的 [应用逻辑] 模块将包含以下元素：

    在 [Application Logic] 块内，我们可以区分

    • [IE=输入接口] 模块，它作为应用程序的入口点。无论客户端类型如何，该模块保持不变。
    • [业务类] 模块，其中包含应用程序逻辑所需的类。这些类与客户端无关。

    • 在 Web 应用程序中，可以通过使用样式表来增强展示层与业务逻辑层之间的分离。样式表控制网页在浏览器中的呈现方式。要更改这种呈现效果，只需修改相关的样式表即可，无需更改业务逻辑。因此，我们将在这里使用样式表。

    评论

    • Article 类使用 PEAR::DB 库访问数据库，因此该命令 
    require_once 'DB.php';

    此包含语句假设 DB.php 脚本位于 PHP 配置文件中 include_path 选项指定的目录之一中。

    • 构建器需要知道连接到哪个数据库以及使用哪个用户身份。这些信息由 $dDSN 字典提供。回顾一下，最初的假设是数据库名为 dbarticles，属于名为 admarticles 的用户，密码为 mdparticles。另请注意，该应用程序支持具有不同权限的多用户。 这里存在一个需要解决的歧义。连接确实是以 admarticles 的身份建立的，而且最终对 dbarticles 数据库的所有操作都将以此身份执行，因为这是 MySQL 数据库管理系统所识别的、拥有管理 dbarticles 数据库足够权限的唯一用户名。 为了“模拟”不同用户的存在，我们将让 admarticles 用户以作为构造函数参数传递的用户（其登录名 $sUser 和密码 $sMdp）的权限进行操作。因此，在对 articles 数据库执行操作之前，我们将验证该用户（$sUser, $sMdp）是否具备必要的权限。如果具备，adarticles 用户将代表其执行该操作。
    • 必须将产品数据库管理员的登录名和密码传递给构造函数。这是一项合理的预防措施。如果将这两项信息硬编码到类中，任何使用该类的用户都可能轻易冒充产品数据库管理员。事实上，PHP 类本身并不受保护。 因此，该类的 $bAdmin 属性——它用于标识当前操作的用户 ($sUser, $sMdp) 是否为管理员——完全可能被外部直接设置，如下例所示： 
    $oArticles=new articles($dDSN,$sUser,$sMdp)
// ici $sUser a été reconnu comme un utilisateur non administrateur de la base
$oArticle->bAdmin=TRUE;
// maintenant $sUser est devenu administrateur

    PHP 并非 Java 或 C#，PHP 类仅仅是一种比字典稍高级的数据结构，但它并不具备真正类所具备的安全性——在真正的类中，bAdmin 属性会被声明为 private 或 protected，从而无法从外部修改。由于该类的用户必须知道文章数据库管理员的登录名和密码，因此只有后者才能使用该类。 因此，前面的操作对他已无实际意义。该类的存在纯粹是为了提供开发便利。一个重要的结果是，无需采取任何安全防范措施。再次强调，任何使用 *articles* 类的人必然是产品数据库的管理员。

    • 该类通过将错误信息填入 $aErrors 属性，以统一方式处理数据库连接错误或其他任何错误。因此，在每次操作后，类的使用者都必须检查该列表。
    • addArticle、updateArticle、deleteArticle、selectArticles 和 execute 这几个方法直接源自前面展示的 Web 界面原型图，它们对应于菜单中的选项。addArticle 和 updateArticle 方法依赖于 verifyArticle 方法，以确保待添加或修改的条目包含正确的数据。同样地，existsArticle 方法可确保我们不会添加已经存在的文章。 如果使用以代码作为主键的 articles 表，则可以省略该方法。在这种情况下，数据库管理系统（DBMS）会自行提示因重复条目导致的添加失败。不过，它通常会显示一条难以理解且为英文的错误信息。
    • 待修改或删除的条目将通过其唯一代码进行标识。`getCodes` 方法用于检索所有这些代码。
    • disconnect 方法会关闭与数据库的连接，该连接是在创建对象时建立的。我们认为这里没有必要使用 connect 方法，因为它会重新建立与数据库的连接。这使我们能够使用同一个对象随心所欲地打开和关闭连接。只有在与 Web 应用程序结合使用时，这一优势才会显现出来。 应用程序将创建一个 items 对象并将其存储在会话中。虽然会话能在连续的客户端-服务器交互中保留该对象的大部分属性，但无法保留代表已打开连接的属性。因此，每次新的客户端-服务器交互时都必须重新打开该连接。 我们将请求持久连接，使已建立的连接被存储在连接池中并永久保持打开状态。这样，当脚本请求新连接时，系统将从连接池中获取该连接。因此，我们实现了与会话能够存储已建立连接时相同的效果。
    • `existeUser` 方法允许构造函数确定由密码 `$sMdp` 标识的用户 `$sUser` 是否实际存在。如果存在，该方法会检查用户是否为管理员（如 `USERS` 表中所示），并将此信息存储在 `$bAdmin` 属性中。 如果用户不是管理员，该方法将从 DROITS 表中检索其权限，并将其存储在 $dDroits 属性中，该属性是一个双索引字典：如果用户 $sUser 对 $table 拥有 $permission 权限，则 $dDroits[$table][$permission] 为 'y'，否则为 'n'。

    编写 articles 类。数据库访问将通过 PEAR::DB 库处理，该库允许您独立于具体的数据库类型进行操作。

    7.5.2. 客户端请求的典型处理流程

    客户端通过模板页面第2区域中的链接与应用程序进行交互。这些链接将属于以下类型：

    apparticles.php?action=xx&phase=y&PHPSESSID=zzzzzzzzzzzz

    action
    指以下选项中的当前操作：
    authenticate
    客户端身份验证
    选择文章
    选择项目（查看）
    更新文章
    更新项目
    删除文章
    删除文章
    SQL
    执行任意 SQL 查询（管理员）
    阶段
    操作可分多个步骤执行——指当前步骤
    PHPSESSID
    会话开始时的会话令牌——允许服务器检索先前交互中存储在会话中的信息

    同样，表单中的 action 属性也将采用相同的格式。例如，在首页的第 4 部分有一个登录表单。该表单的 HTML 标签定义如下：

    <form name="frmLogin" method="post" action="apparticles.php?action=authentifier&phase=1">

    客户端的请求由应用程序的主脚本（名为 apparticles.php）处理。该脚本的任务是构建返回给客户端的响应。其处理流程始终如下：

    • 根据操作名称和当前阶段，它将把请求转发给一个专门的函数。该函数将处理请求并生成相应的响应页面。 对于每个客户端请求，可能存在多个潜在的响应页面：page1、page2、...、pagen。这些页面包含必须由函数计算生成的信息，因此属于参数化页面。它们将由脚本 page1.php、page2.php、...、pagen.php 生成。
    • 为保持一致性，模板页面第 4 区中要显示的页面可变部分也将放入 $main 字典中。

    假设服务器在响应请求时，必须向客户端发送页面 pagex.php。其操作流程如下：

    • 它将 pagex.php 页面所需的值放入 $main 字典中
    • 将 $main['content']（该字段指定要在模板页面的第 4 区域显示的页面的 URL）设置为 pagex.php 的 URL
    • 它将通过以下指令请求显示模板页面 
    include "main.php";

    7.7.2. 提升安全性

    在开发 Web 应用程序时，切勿假设客户端是浏览器，也切勿认为其发送的请求受您在该请求之前发送的表单所控制。任何程序都可能充当 Web 应用程序的客户端，从而向应用程序发送任何请求——无论是否带参数。因此，应用程序必须对所有内容进行验证。

    如果查看 apparticles.php 脚本中的代码，我们会发现

    • 在没有会话的情况下，除了身份验证之外无法进行任何操作。只有当用户成功通过身份验证时，会话才存在。 请记住，会话通过一个称为会话令牌的较长字符串来标识，其格式如下：176a43609572907333118333edf6d1fb。该令牌可以通过多种方式发送给应用程序，例如使用带参数的 URL： 
    
apparticles.php?PHPSESSID=176a43609572907333118333edf6d1fb.

    考虑到可能的组合数量极其庞大，如果某个程序通过随机更改令牌值并反复请求上述 URL 来寻找正确组合，很可能需要数天时间才能生成正确的组合。届时，由于会话有效期有限，该组合极有可能已经过期。另一个风险是，通过网络以明文形式传输的令牌可能会被截获。这确实是一个现实的风险。因此，可以在服务器与其客户端之间建立加密连接。

    • 会话建立后，仅允许执行特定操作。配置为 action=cheat&phase=0&PHPSESSID=[PHPSESSID] 的 URL 将被拒绝，因为“cheat”操作并非授权操作。当参数（action、phase）无法识别时，我们的应用程序将返回身份验证页面。

    然而，应用程序不会验证授权操作是否遵循正确的顺序。例如，以下两个操作：

    1. action=addArticle&phase=0&PHPSESSID=[PHPSESSID]
    2. action=updateArticle&phase=1&PHPSESSID=[PHPSESSID]

    是两个已授权的操作。但操作 2 无权紧随操作 1 之后执行。

    如何追踪客户端浏览器请求的 URL 序列？

    我们可以使用两个 PHP 变量：$_SERVER['REQUEST_URI'] 和 $_SERVER['HTTP_REFERER']，它们是客户端浏览器在 HTTP 头部中发送的两项信息。

    $_SERVER['REQUEST_URI']：这是客户端请求的 URI。例如

    /apparticles.php?action=addArticle&phase=0&PHPSESSID=[PHPSESSID]

    $_SERVER['HTTP_REFERER']: 这是浏览器在当前请求的新 URL 之前所显示的 URL（即之前的 URI）。例如，如果显示上述 URI 的浏览器向服务器发起了一个新请求，则该请求的 $_SERVER['HTTP_REFERER'] 变量将取值为 

    http://machine:port//apparticles.php?action=addArticle&phase=0&PHPSESSID=[PHPSESSID]

    要验证应用程序中的两个操作是否按顺序执行，我们可以按以下步骤操作：

    在操作 1 期间：

    • 记录请求的 URI（URI1）并将其存储在会话中

    在操作 2 期间：

    • 获取操作 2 的 HTTP-REFERER。据此，我们推导出发起请求的浏览器中先前显示的 URL 的 URI（URI2）。
    • 检索存储在会话中的 URI（URI1），即之前向服务器请求的操作的 URI
    • 如果操作 2 紧随操作 1 之后，则 URI2 必须等于 URI1。如果情况并非如此，我们将拒绝执行所请求的操作并显示身份验证页面。
    • 我们将当前操作的 URI（URI2）存储在会话中，以便验证后续操作。以此类推。

    以下是一个示例。认证通过后，我们点击 [添加文章] 链接：

    该页面的 URL 为：

    http://localhost:81/st/php/articles/gestion/articles8/apparticles.php?action=addArticle&phase=0&PHPSESSID=006a63e6027f16c70b63cdae93405eeb

    直接在浏览器的 [地址] 栏中，我们将 URL 修改如下：

    http://localhost:81/st/php/articles/gestion/articles8/apparticles.php?action=deleteArticle&phase=1&PHPSESSID=006a63e6027f16c70b63cdae93405eeb

    这种机制对网页浏览器效果良好，但对编程客户端则完全行不通。编程客户端可以发送任意内容的 HTTP_REFERER 头部。因此，它可以“作弊”，声称自己已经完成了某个步骤，而实际上并未完成。 因此，您必须确保操作步骤的顺序得到遵守。例如，如果请求的操作是 action=addArticle&phase=1（添加），那么前一个操作必须是 action=deleteArticle&phase=0（初始请求进入页面）或 action=addArticle&phase=2（添加失败后返回）。 同样地，如果请求的操作是 action=addArticle&phase=2（添加），那么前一个操作必须是 action=addArticle&phase=1（进入）。我们可以强制用户遵循这些顺序。

    7.7.4. 提升性能

    目前，我们选择使用轻量级客户端浏览器：它仅负责显示内容。我们可以通过在发送给它的网页中嵌入脚本，使其执行处理任务。这些脚本可以使用多种语言编写，尤其是 VBScript 和 JavaScript。Internet Explorer 和 Netscape 占据了浏览器市场的大部分份额，比例约为 60:40。此外，IE 仅在 Windows 系统上可用，而在 Unix 等系统上则不可用，而 Unix 系统上 Netscape 占据主导地位。 Netscape 无法原生执行 VBScript，而这两款浏览器均可执行 JavaScript。鉴于 Netscape 仍占据浏览器市场的重要份额，应避免使用 VBScript。因此，客户端脚本通常采用 JavaScript。

    无需服务器干预的处理任务将交由客户端脚本完成。在我们的应用程序中，客户端浏览器应在验证请求后才向服务器发送请求，这样更为合理。因此，如果用户在身份验证表单中留空了 [login] 字段，向服务器发送身份验证请求便毫无意义。此时，应通知用户其请求无效：

    7.8. 延伸阅读

    最后，以下是几个扩展本案例研究的思路：

    • 探索将该应用程序的标准页面转换为一个类，并将其应用于其他应用程序，将是一件很有趣的事情。
    • 我们的应用程序非常适合基于浏览器的客户端，但不太适合“独立应用程序”客户端。后者必须：
      • 与服务器建立 TCP 连接
      • 通过 HTTP 与其“通信”
      • 解析服务器的 HTML 响应以查找所需信息，因为独立客户端通常不会关注那些专为浏览器设计的呈现用 HTML 代码。

    对于我们的应用程序而言，生成 XML 而不是 HTML 会更有益处。这样一来，其客户端既可以是浏览器（至少是较新的版本），也可以是独立应用程序。对于后者而言，查找所需信息将毫无困难，因为服务器的 XML 响应中不包含任何呈现信息，只有内容。

    • 我们当然需要解决文章数据库的并发访问问题。至少有两点需要澄清：
    1. 应用程序所使用的数据库管理系统（DBMS）能否妥善处理对同一文章的并发访问？例如，如果两名用户同时编辑同一文章（他们同时点击了[编辑]按钮），会发生什么情况？这很可能取决于底层的DBMS。
    2. 目前，我们的应用程序尚未处理并发访问。不过，即使可能会出现一些意外行为，数据库仍应保持一致状态。请考虑以下事件序列：
        • 用户 U1 开始编辑一篇文章
        • 用户 U2 随后开始删除同一文章
        • 这些操作均需进行客户端与服务器的通信。根据每位用户的操作习惯，用户 U2 可能在 U1 之前完成任务。当 U1 完成编辑并点击 [编辑] 保存时，系统将返回信息页面，数据库管理系统会显示 [0 行被修改]，因为用户原本打算编辑的页面在此期间已被删除。用户很可能会感到惊讶。 从可用性角度来看，最好显示一个能更清晰地说明错误的页面。此外，还可以考虑在用户开始更新文章时，立即授予其对该文章的独占访问权限。 此时，若其他用户尝试编辑同一文章，系统将提示“正在进行编辑”。如果首位用户延迟保存更改，这将导致其他用户被阻塞。此处需要寻找解决方案，且这些方案在很大程度上取决于所用数据库管理系统（DBMS）的功能。例如，Oracle 在这方面的功能就比 MySQL 更强大。
